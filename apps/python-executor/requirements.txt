# ML model hosting — required to unpickle and run uploaded models (advertised
# feature + /models UI + policy "model" step). Without these the runtime cannot
# deserialize real models. Full stack (sklearn + boosted trees); adds ~400MB.
# macOS note: xgboost and lightgbm link against libomp.dylib, which is NOT bundled
# in their wheels. Without it `import xgboost` fails with "Library not loaded:
# @rpath/libomp.dylib" and ML model hosting is silently unavailable. Install it with
#   brew install libomp
# (Linux wheels bundle their own OpenMP, so the Docker image needs nothing extra.)
# numpy: the ceiling is a PYTHON-VERSION fact, so it is expressed as one rather than left as a
# note in a doc. numpy 2.5.x requires Python >= 3.12; this project runs 3.11 (Dockerfile:
# python:3.11-slim), where the newest installable release is 2.4.6.
#
# Written as markers because the failure it prevents is loud but misleading: a bare `numpy==2.5.4`
# makes pip abort the ENTIRE install with "Could not find a version that satisfies the
# requirement", which reads as a broken requirements file rather than "this pin needs a newer
# interpreter". Dependabot has now proposed exactly that twice -- PR #170 and PR #171 -- and the
# first was initially reported as PASSING 1937 tests, because the verification harness used `;`
# instead of `&&` after pip install and the suite ran against the numpy already in the venv.
#
# Same shape as the scipy pins below, and self-correcting: if this project moves to 3.12+, the
# second line takes over with no edit here.
#
# BE CLEAR ABOUT WHAT IS TESTED. Only the first line is: every lane runs 3.11. The 3.12 line is
# the documented forward path, not a verified configuration -- whoever moves the runtime has to
# re-check it, along with scikit-learn, which pins its own supported numpy range.
numpy==2.4.6; python_version < "3.12"
numpy==2.5.4; python_version >= "3.12"
# scipy: ONE dimension, the Python version -- and getting that wrong cost a full regression run.
#
# This was four cells split on `sys_platform` AND `python_version`, with darwin < 3.12 pinned to
# 1.15.1 and a comment saying "on modern macOS (Darwin 27 / py3.13) the 1.15.1 wheel fails to
# dlopen, so newer interpreters take 1.18.0 there".
#
# That comment identified the right FAILURE and the wrong CAUSE. It is not the interpreter, it is
# the OS: when this machine was upgraded to Darwin 27 the existing Python 3.11 venv started
# failing, because the 1.15.1 wheel's `_spropack.so` will not load under the newer dyld --
#
#     ImportError: dlopen(.../scipy/sparse/linalg/_propack/_spropack.cpython-311-darwin.so):
#     section '__DATA/__thread_bss' has a zero-fill section type, but offset field is not zero
#
# The gate was on python_version, so an OS upgrade walked straight past it and took out the whole
# Python lane -- 2064 tests, one error, in a module nothing had changed.
#
# 1.17.1 is the newest release supporting 3.11, it loads on Darwin 27, and scikit-learn 1.9.1
# accepts it. It also works on Linux, which is what collapses this back to one axis: the platform
# split existed only to work around a version that was simply too old. Fewer cells, and none of
# them gated on the dimension that was never the cause.
#
# TESTED: the first line, on darwin 27 / py3.11 and in the python:3.11-slim image. The >= 3.12
# line is the documented forward path, unverified, exactly like numpy's above.
scipy==1.17.1; python_version < "3.12"
scipy==1.18.1; python_version >= "3.12"
